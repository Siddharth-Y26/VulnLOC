SECTION 01

The project in one minute

Programs contain security bugs. Tools exist to find them, but almost every tool answers the wrong question. They say “this function is risky.” A function can be 200 lines long. The developer still has to find the bug by hand.

We are building a tool that says: the bug is on line 45, and here is why.

The idea in everyday terms

Imagine two specialists reviewing the same code.

  • The first specialist reads the code like text. They have read millions of lines, so they recognise phrasing that usually means trouble. They do not really understand how the program runs — they recognise patterns. This is the LLM.
  • The second specialist ignores the words and draws diagrams — what runs after what, and where each value travels. They understand structure, but they miss meaning. This is the GNN.

Almost every existing system takes one report from each specialist and staples them together. We put the two specialists in a room and make them discuss the code line by line before either writes anything down. That conversation is called cross-attention, and proving it beats stapling is the entire point of the project.

For them to talk to each other, they need to agree on what they are pointing at. So both are forced to describe everything in terms of line numbers. We call this the shared line axis. It sounds like a small engineering detail. It is actually the foundation the whole design rests on, and most of our work so far has been making sure the line number never gets lost.

SECTION 03

The problem we are solving

What exactly is the problem?

Existing vulnerability detectors mostly work at the level of a whole function. They output one yes/no answer for a block of code that may be hundreds of lines long. That output is not actionable: a developer who is told “something here is wrong” still has to do the hard part themselves.

On top of that, when these tools do try to explain themselves, they produce a heatmap of which words the model looked at. Looking at a word is not the same as having a reason. Developers do not trust it, so they ignore it.

Why does this matter enough to be a project?

Because trust is the bottleneck, not accuracy. Security teams already have tools that produce huge numbers of alerts. The reason those tools get switched off is that checking each alert costs more than it saves. A tool that points at one line and gives a reason changes the economics of the review. A tool that flags a function does not.

There is also a research gap, which is what makes it a project and not just engineering: the two useful sources of evidence — what code means and how code behaves — are almost never made to interact properly. They are combined by stapling. Nobody has run a fair, controlled test of whether a deeper interaction is better.

How do we solve it?

Three moves, in order:

1. Force everything onto line numbers. The text model and the graph model both report per line, so their outputs are directly comparable.
2. Let them interact before deciding. Bidirectional cross-attention on that shared line axis, rather than concatenation after the fact.
3. Only explain what we can point at. An explanation must cite lines and symbols that actually exist in the code and were actually used by the model. If we cannot ground it, we do not show it.

The five gaps we are addressing (memorise these five words)

  1. Granularity — function-level output is not usable.
  2. Explainability — heatmaps are not reasons.
  3. Fusion — semantic and structural views never truly interact.
  4. Ground truth — line-level labelled data barely exists.
  5. Trust — developers ignore output they cannot verify.
SECTION 04

The datasets

This is the section panels probe hardest, because it is where projects usually cut corners. We use five datasets, each with exactly one job, and they never share data.

DatasetIts one jobWhy this oneLine labels?
Big-VulTrain the modelThe only public C/C++ set that ships per-line flaw indicesYes
PrimeVul (confirmed)Clean evaluationManually verified labels; measures how much our score is limited by bad labelsNo
DiverseVulGeneralization testProjects that do not appear in Big-Vul at allNo
PrimeVul pairedSanity validationSame function before and after the fix — a real test of understandingNo
Juliet 1.3.1Pipeline testing onlyArtificial code with perfect labels; good for unit tests, never for headline claimsYes

What is Big-Vul, and why is it the main dataset?

What: 188,636 real C/C++ functions collected from real projects, linked to real published CVEs. 10,900 of them are vulnerable (5.78%).

Why: One hard requirement drove the choice — we need to know which lines are vulnerable, not just which functions. Big-Vul is effectively the only public C/C++ distribution that provides that. Without it there is no project. Everything else was secondary.

How the line labels exist at all: when a project fixes a security bug, it commits a patch. The lines that patch removed or changed are, by reasonable inference, the vulnerable lines. Big-Vul recorded those positions.

Why C and C++ and not Python or Java?

Two reasons. First, the data: line-labelled vulnerability corpora are overwhelmingly C/C++, so the choice was largely made for us by the ground-truth requirement. Second, the language: C and C++ have manual memory management, so the classic serious vulnerability classes — buffer overflows, use-after-free — are exactly the ones that structural analysis of data flow is good at catching. It is the right domain for the method, not just the convenient one.

How did you split the data into train, validation and test?

What we did: a project-wise 80/10/10 split. Every function from a given project goes entirely into one split. Result: 148,983 train / 18,593 validation / 18,442 test, plus withheld sets.

Why not a random split: code repeats itself. The same function appears many times across a project's history. A random split would put near-identical functions in both train and test, and the model would score brilliantly by memorising. That is data leakage, and much of the published literature suffers from it. Project-wise splitting is the harder, honest number, and we lead with it.

How we made it reproducible: we assign each function by hashing its content, not by shuffling with a random seed. A shuffle gives a different answer if the input file order ever changes; a content hash does not. Re-running the split script verifies the previous result byte for byte — a different answer is treated as a bug, not as a new experiment. The split has a fingerprint: 0ade7483…

How do you know there is no leakage?

We measured it, and we report three numbers: 0 projects shared across splits, 0 duplicate function hashes across splits, 0 clean-evaluation functions present in training.

We also found something worth mentioning, because it shows we looked properly: a project-wise split does not fully stop leakage. Open-source code gets forked and copied between projects, so 426 functions were byte-identical across different projects. We removed them. And because we only detect exact matches, that number is a floor, not a ceiling — near-duplicates certainly remain.

Do not say this by mistake

Do not describe PrimeVul as an independent dataset. PrimeVul was built from Big-Vul and others, so it is not disjoint from our training data. It measures label quality, not generalization. DiverseVul is the generalization test. Mixing these two up is the single easiest way to lose credibility in this section.

SECTION 05

Labels, noise, and honesty

Our strongest section, and counter-intuitively it is a section about our data being bad. Panels reward a team that knows the limits of its own evidence.

What is label noise here, and how bad is it?

What: the labels say which lines are vulnerable. They were derived from fix commits. But a fix commit often does more than fix — it renames variables, reformats code, tidies up. All those lines get marked vulnerable too, even though they are not.

How bad: we hand-checked a sample of 20 labelled functions ourselves. 6 of 20 were wrong — about 30%. Because the sample is small, the honest range is 14.5% to 51.9%.

Why it matters: this is a ceiling on every line-level number we will ever report. If roughly a third of the answer key is wrong, a perfect model cannot score 100%. We will state this next to our results rather than quietly hoping nobody asks.

The three ceilings — keep them separate, never add them up

A panel may try to merge these. They are different measurements of different things:

  1. ~30% of line labels are wrong (from our own audit of 20 functions). This is different from, and larger than, the 19.2% function-level noise rate.
  2. 7.84% of flagged lines have no graph node, so the structural branch physically cannot score them. 84.8% of those are in code our parser could not fully parse — so it is parse damage, not empty lines.
  3. Cutting input at 512 tokens loses 38.1% of flagged lines (44.5% on the evaluation set). We fixed this with windowing, which keeps 100%.

Why did you audit the labels yourselves instead of trusting the dataset?

Because published work already warned us. One study found 20–71% label inaccuracy across public vulnerability datasets; another independently estimated 40–75%. We could have cited those and moved on. Instead we measured our own corpus, because a number from someone else's dataset is not evidence about ours.

We also checked the labels for consistency and found it perfect: zero out-of-range line numbers, zero text mismatches, zero labels on non-vulnerable functions. That is worth saying carefully — consistency is not correctness. The labels are internally coherent and still about 30% wrong.

If the labels are 30% wrong, is the project worth doing?

Yes, and the noise is part of the contribution. Three points:

One: our core experiment is a comparison — cross-attention versus concatenation on identical data. Both sides face the same noisy labels, so the comparison stays valid even though the absolute numbers are capped.
Two: that is exactly why we hold out a manually confirmed clean evaluation set — to see how much of our error is the model and how much is the answer key.
Three: most papers in this area report absolute numbers on this same data without mentioning the ceiling. Quantifying it is a stated contribution, not an excuse.

SECTION 06

The graphs, seen and explained

Yes — the graphs are real and they are visualizable. What follows is one genuine function from our test set, drawn four different ways. This is generated directly from our pipeline, not illustrated by hand.

How to read the pictures

These are not the usual tangled ball-of-string graph drawings. We laid them out deliberately:

  • Going down = the source lines, in order. Row 5 in the picture is line 5 of the code beside it.
  • Going across = position within that line, roughly where the code sits.
  • Dots are nodes — pieces of the program.
  • Curves are edges — relationships between those pieces.
  • The red row is the known vulnerable line from the ground truth.

Drawing it this way is the point: it makes our central claim visible. Every dot sits on the line it belongs to. That is the shared line axis, shown rather than asserted. It is also a debugging tool — if our line mapping ever broke, a dot would appear on the wrong row and we would see it immediately.

Unit:

problem_data_save()1 of 17 lines flagged
AST edge CFG edge DFG edge call edge known vulnerable line

The four graph types, in plain language

AST — what, why, how?

What: the Abstract Syntax Tree. Every symbol and every construct in the code becomes a node, arranged by grammar. It is a sentence diagram for code.

Why: it is complete — nothing in the code is missing from it — and it is the base every other graph is built from.

How to read the picture: dense and even. That density is also its weakness. Syntax exists on every line whether or not anything is wrong, so the AST alone gives the model little reason to prefer one line over another. 101 nodes for 17 lines of code.

CFG — what, why, how?

What: the Control Flow Graph. It records what can run after what. An if statement creates a fork; a loop creates a cycle.

Why: it answers “can execution actually get from this line to that one?” A bug that is unreachable is not a bug.

How to read the picture: sparse and mostly vertical, because code mostly runs top to bottom. The branch at line 8 (if (dd)) is visible as the place the flow splits. Only 9 edges — that sparseness is the information.

DFG — what, why, how?

What: the Data Flow Graph. It connects the place a value is created to every place that value is used.

Why: this is the one that matters most for security. Nearly every serious vulnerability is a story about a value travelling from where it enters the program to somewhere it should not reach. Buffer overflows, information leaks, injection — all data flow stories.

How to read the picture: its edges jump across lines rather than running straight down, connecting the allocation on line 5 to the uses below it. That jump is the shape of the CWE-200 information-exposure bug in this very function.

CPG — what, why, how?

What: the Code Property Graph — all three of the above combined into one picture.

Why: real reasoning needs all three at once. “This value comes from there (data flow), execution can reach here (control flow), and this is a memory copy (syntax)” is a complete argument; any one alone is not.

How, and this is the clever part: all four graphs share the same 101 nodes. Only the edges differ. So the CPG is not a new construction — it is literally the union of the others. Practically, that means testing “which graph type matters most?” is a single setting change, not four separate pipelines.

How do you build these graphs? Why not use an existing tool?

How: we parse with Tree-sitter, then build the graphs ourselves on top of the parse tree, with the line number attached to every node from the start.

Why not an off-the-shelf tool: standard analysis tools need code that compiles. Our corpus is 188,636 isolated functions with no headers and no build system — almost none of it compiles. Tree-sitter parses broken code and recovers, which is the only way to work at this scale. The trade-off is honest and we state it: our data flow analysis is name-based. It matches variables by name, so it does not track pointer aliasing or scoping precisely. We will never claim the model “follows data flow” without that caveat.

Which grammar do you parse with — C or C++?

A question that sounds trivial and was one of our most important findings.

What we found: the dataset has a language column, and 98.6% of it says “C”. Trusting it gives a clean parse rate of only 37.01%. Parsing everything as C gives 35.74%. Parsing everything as C++ gives 88.24%.

What we do now: try C++ first, and if damage remains, try C too, and keep whichever tree is less damaged. That reaches 89.14%. Ties go to C++, so the choice depends only on the source code — making it fully reproducible.

Why it matters: we more than doubled our usable data by questioning one column. The lesson we would offer a panel: the dataset's own metadata was the worst available way to make this decision, and we only found that out by measuring all the options instead of assuming.

The honest caveat about the example above

This function was picked by a filter, not by eye: first one in the test set between 12 and 34 lines, parsing cleanly, with both control and data flow present, and with under 35% of lines flagged. That last condition was added after the first candidate came back with 19 of its 21 lines marked vulnerable — a whole function flagged because the fix commit rewrote all of it. If asked whether we cherry-picked: we filtered, we can state the filter exactly, and the rejected example is itself evidence of the label-noise problem.

SECTION 07

The methodology, step by step

Seven stages. Be able to say these in order.

StepWhat happensWhy it is there
1Parse the function into a syntax treeNothing structural is possible without this
2Build AST, CFG and DFG over one shared node setGives us the structural view, and makes the CPG a free union
3aSemantic branch: chop code into tokens, feed to CodeBERTProduces meaning-aware numbers per token
3bStructural branch: run a GNN over the graphProduces structure-aware numbers per node
4LineAligner: pool tokens by line, pool nodes by lineThe two branches now speak the same language: one vector per line, each
5Bidirectional cross-attention between the twoThe novelty. The two views interact before any decision
6Score every line, and score the function; train on bothLine scores are the goal; the function score is extra supervision
7Generate an explanation that must cite real lines and symbolsPrevents a fluent, confident, invented answer

What is the LineAligner and why is it the most important module?

What: a component that takes token-level output from the LLM and node-level output from the GNN, and converts both into one vector per source line.

Why: without it the two branches cannot be compared at all. The LLM's units are token positions; the GNN's units are graph nodes; these do not correspond. The only thing both agree on is the line number. Everything before this module exists to keep the line number intact; everything after exists because it survived.

How: every token knows which byte range it came from, and every node knows which byte it starts at; a line map converts bytes to line numbers. Then all tokens on line 5 are pooled together, and all nodes on line 5 are pooled together.

What is “windowing” and why did you need it?

What: CodeBERT can only read 512 tokens at a time. Long functions exceed that. The usual response is to cut off the rest. Instead we slide a window along the function and process it in overlapping pieces.

Why: we measured what cutting off costs and it was alarming — 38.1% of all vulnerable lines were being thrown away, and 44.5% on our evaluation set. You cannot localize a line you never read. Windowing keeps 100%.

How, and the practical consequence: one function is no longer one forward pass. Our evaluation functions average 4.17 windows, and the longest is 287. So we batch by window, not by function — a detail that would have silently broken our memory budget if we had assumed otherwise.

How do you train it, and on what hardware?

How: supervised learning. The model predicts a score per line, we compare against the known vulnerable lines, and adjust. We train on two objectives at once — per line and per function — because the function label is available for far more data than the line labels are.

Hardware: one laptop GPU with 4 GB of memory, which is genuinely tight for a transformer plus a GNN. We measured our way to a configuration that fits: mixed precision plus gradient checkpointing, batches of 16 windows, peaking at 2,456 MB and running at 22.9 windows per second.

A trap we documented: on Windows, running out of GPU memory does not produce an error. It silently spills into system memory and runs 10–25× slower. Three of our 24 test configurations exceeded the card and still “worked”. So we compare peak memory against card capacity — “it did not crash” is not the same as “it fits”.

How do you handle the fact that vulnerable lines are so rare?

The problem: only 0.795% of source lines are vulnerable. A model that predicts “clean” for every single line would be 99.2% accurate and completely useless.

What we do about it: two things. In training, we test weighted and focal loss functions that make the rare positive cases count for more. In evaluation, we refuse to lead with accuracy — we use PR-AUC, Top-5, and IFA, which cannot be gamed by always saying “clean”.

SECTION 08

The novelty: cross-attention

If you remember one section for the panel, make it this one.

Concatenation vs. cross-attention, without any maths

Concatenation is what almost everyone does. The text model writes its summary. The graph model writes its summary. You place the two summaries side by side and hand them to a decision-maker. The two models never communicated. Neither one's opinion changed because of the other.

Cross-attention puts them in conversation, line by line, in both directions:

  • The text model asks the graph: “I find line 10 suspicious — structurally, does anything flow into line 10?”
  • The graph answers: “Yes, the value used on line 10 was created on line 5, and nothing checked its size in between.”
  • And the reverse: the graph asks the text model whether the operation on line 10 is the kind that is dangerous with unchecked input.

Both views get updated by the other before anything is decided. That is the whole difference, and “bidirectional” simply means the asking goes both ways.

Why do you believe this will be better?

Because the evidence for a vulnerability is usually split across the two views. Neither “this is a memory copy” nor “this value came from user input” is alarming alone. Together they are a buffer overflow. Concatenation asks a final classifier to notice the combination from two compressed summaries. Cross-attention lets the combination be formed at the point where the detail still exists — per line, before pooling.

Note the wording: we say we believe. We have not yet run the experiment. Claiming the result before measuring it is precisely what our project rules forbid.

How will you prove it isn't just extra parameters making things better?

This is the right question, and the experiment is designed around it. Experiment A1 compares five fusion strategies — cross-attention, concatenation, sum, gated, and none — under identical data, identical encoders, identical training budget, and identical hyperparameter tuning effort on both sides.

The tuning point is the one that matters most. If we tuned cross-attention carefully and the baseline carelessly, our result would be meaningless. So the search budget is fixed and written down before the experiment. We also include gated and sum fusion specifically to rule out “any fusion helps” as the real explanation. Five random seeds, mean and standard deviation, significance tested.

What if cross-attention loses?

We report that it lost. This is written into our project rules and is not a fallback position invented for this question.

And the work still stands, because the contribution is then: a controlled comparison the literature has not run, a line-level evaluation protocol, a quantified label-noise ceiling, and an open framework where new fusion methods plug in by configuration. A negative result that is properly controlled is more useful to the field than a positive result that is not.

SECTION 09

The system and its modules

The code is organised in layers, and a layer may only use layers below it. Data preparation cannot reach up into modelling; modelling cannot reach up into training.

LayerModuleWhat it does, plainlyStatus
L6servingThe demo — where a user pastes code and gets an answernot started
L5explanationWrites the reason, and refuses to write one it cannot back upnot started
L4evaluationScoring, ablations, statistical testsnot started
L3trainingThe training loop, loss functions, experiment trackingbuilt
L2modelsThe LLM branch, the GNN branch, the LineAligner, the fusionpartly built
L1representationParsing, line mapping, all four graph builderscomplete
L0dataDownloading, labelling, splitting, cachingcomplete

Why organise it this way? Isn't it over-engineering for a student project?

Two concrete payoffs, not aesthetics.

One — the layering is enforced by a tool, not by discipline. If someone writes an import that goes the wrong way, the build fails. Architecture that is only written in a document decays; this cannot.

Two — every experiment is a configuration change, never a code edit. Swapping the graph type, the GNN, or the fusion method is one line in a config file. This is what makes ten ablation studies feasible for a small team, and it means no experiment can accidentally change the model it was supposed to be comparing against.

How do you make sure results are reproducible?

Four mechanisms:

1. The data split is content-hashed and re-running it verifies rather than regenerates.
2. Every number we report must trace to a logged run ID. A figure without a run behind it does not go in a slide.
3. 568 automated tests, plus formatting, linting and type checking, all passing. Tests target failure modes, not just the happy path.
4. Unfinished code raises an error rather than returning a plausible-looking fake result — so an unfinished component cannot silently produce a number.

Where is the project right now?

Phase 1 (data): complete. Dataset selected, built, split, leakage-checked, hand-audited.
Phase 2 (representation): complete. Parser, line mapping, all four graph builders, corpus-wide measurement.
Phase 3 (semantic branch): 3 of 4. Encoder, line head, losses, metrics and the training loop all built. The sanity test passes — we deliberately overfit 32 samples and reached Top-5 = 1.0, proving the learning path works end to end. Remaining: the full LLM-only baseline over at least three seeds.
Phases 4–10: the GNN branch, fusion, explanation, evaluation and demo. Phase 4 is unblocked and next.

SECTION 10

How we will judge it

We committed to our headline metrics before seeing any results. That is deliberate: it stops you from running everything and then picking whichever measure flatters you.

Top-5 accuracy

Is a genuinely vulnerable line among our 5 highest-scored lines? This mirrors how someone actually uses the tool — they check the top few.

IFA — Initial False Alarms

How many clean lines does a developer inspect before hitting a real one? This is trust, measured directly. High IFA means the tool gets switched off.

Line-level PR-AUC

Overall quality of the ranking, without needing a threshold, and honest when positives are under 1% of the data.

Recall@k%LOC

How many real bugs we catch if the reviewer only has time to check the top 5% of lines. A real budget, not an unlimited one.

Why not just report accuracy and F1?

Because 0.795% of lines are vulnerable. Saying “clean” to everything yields 99.2% accuracy while finding nothing. We report accuracy for completeness and never lead with it. PR-AUC is the honest curve at this level of imbalance, and MCC is far harder to game than F1.

How will you test whether the explanations are real and not invented?

Two independent checks, because “the explanation sounds convincing” is not evidence.

Grounding rate (automatic): what percentage of explanations cite only lines and symbols that genuinely exist in the code? This is fully checkable and always available.

Faithfulness (the harder one): if we delete the lines the model claims to rely on, its confidence should collapse. If we delete random lines, it should not. If deleting the “important” lines changes nothing, the explanation was decoration. We also check whether attention weights and gradient-based importance agree.

Is attention an explanation?

No, and we are careful about this. Attention shows what the model looked at, not what it depended on. It is a hypothesis about the model's reasoning. That is exactly why we run the deletion tests above — to test the hypothesis rather than assume it. Treating attention as self-evidently explanatory is a known weakness of prior work.

The five sentences that carry the whole talk

  1. Existing tools say this function is risky; developers need this line, and why.
  2. Meaning and structure are both useful, but they are almost always stapled together instead of made to interact.
  3. We force both onto a shared line axis and let them attend to each other in both directions before deciding anything.
  4. The load-bearing experiment is cross-attention versus concatenation under identical conditions — and we will report the result either way.
  5. We measured our own data's limits first, so every number we publish will come with its ceiling attached.

Hard questions, honestly answered

You have no results yet. What have you actually done?

Two complete phases and most of a third. Concretely: the corpus is built, split without leakage, and hand-audited; all four graph types are implemented and measured across the whole corpus; the semantic branch, line head, losses, metrics and training loop are written and pass an end-to-end sanity test.

We also produced findings along the way, not just code: the grammar-selection result that took usable data from 37% to 89%, the truncation measurement that saved 38% of our labels, and the label-noise audit. Building the measurement apparatus before the model is deliberate — a result from an unvalidated pipeline is not a result.

Isn't this just LineVul with a GNN bolted on?

No, and the difference is where the fusion happens. LineVul is a function-level classifier whose line scores are extracted afterwards from attention; it uses no structure at all. LineVD is the opposite — structure-first, with the language model as a feature source. Both keep the two views separate.

Our claim is specifically about when the two interact: bidirectionally, on a shared line axis, before pooling — and, critically, measured against concatenation under matched conditions. That controlled comparison is what nobody has published.

Why should we believe your numbers over the published ones?

Because we will reproduce every baseline under our own splits rather than quoting numbers from papers. Published figures are frequently measured on random splits, which leak. Any number we take from a paper will be labelled as reported and never mixed into a table with ours.

Can you handle real-world code, or only this dataset?

Honest scope: C and C++, one function at a time, with no cross-function analysis yet. About 10.86% of functions do not parse cleanly under any grammar, and those hold a disproportionate 31.58% of all flagged lines because they are much longer than average. That is a stated limitation, and quoting the smaller 10.86% figure alone would understate it.

We plan a cross-dataset generalization test on DiverseVul precisely because single-dataset results do not establish real-world capability.

What is the biggest risk to this project?

That cross-attention shows no significant improvement over concatenation. It is the honest answer, we have planned for it, and the reporting is committed in advance.

The second risk is the label-noise ceiling limiting how high any line-level number can go — which is why the clean evaluation set exists, to separate our model's error from the answer key's error.

If you do not know an answer
