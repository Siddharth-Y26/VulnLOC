## 0. The one-minute version

We are building a system that points at the **specific lines** of a C/C++ function that carry
a vulnerability, and explains why. It has two halves: a **language model** that reads the code
as text, and a **graph neural network** that reads its structure. Both are projected onto the
same line axis and fused with **bidirectional cross-attention** — that fusion is the novelty.

**Where we are:** the data layer, the representation layer and both single-branch baselines
are finished and measured over three seeds each. The fusion layer is built, tested and
deliberately not yet run. That is **phases 0–5 of 0–10** — approximately half the approved
scope, which is what this review asks for.

**The headline numbers**, on held-out `val`, three seeds each:

| | Semantic (LLM-only) | Structural (GNN-only) |
|---|---|---|
| Top-5 accuracy | **0.6141 ± 0.0055** | **0.4302 ± 0.0372** |
| Line F1 | 0.3692 ± 0.0204 | 0.1077 ± 0.0083 |

**The one sentence to lead with:** *prior line-level results were measured against noisy

# CRITERION 2 — TECHNICAL ACCURACY (5 marks)

> *Uses technically correct methods, algorithms, parameters, and implementation practices
> consistent with the approved design.*

## 2.1 The method, in the order the data moves

1. **Source normalization (ADR-006).** Every line is stripped of leading and trailing
   whitespace at the L0→L1 boundary. *Non-obvious and load-bearing — see §2.6.*
2. **Parsing (ADR-005).** Each function is parsed with **whichever of two tree-sitter
   grammars parses it best** — C++ first, then C if damage remains, keeping the less damaged
   tree. Measured corpus-wide: `declared` 37.01%, C 35.74%, C++ 88.24%, **best-of-two 89.14%**.
3. **Line mapping.** Every token and every graph node carries its source line. This is the
   atomic invariant of the project and is property-tested with `hypothesis`.
4. **Graph construction.** AST → CFG → DFG, with the CPG as their literal union. **All four
   share one node set**, so `node_to_line` is identical across them and the ablation over
   graph types is an argument, not a second construction.
5. **Semantic branch.** CodeBERT (124.6M params) over **sliding windows** of 512 tokens,
   stride 128 — not truncation (§2.5).
6. **Structural branch.** GCN/GAT/GGNN over the graph, node features = node type + identifier
   subtokens.
7. **Line alignment.** Token states and node states are both `scatter_mean`-pooled onto a
   shared **line axis**, which is what makes the two branches combinable at all.
8. **Fusion.** Bidirectional cross-attention between the two line-aligned sequences.
9. **Head.** A shared per-line scorer producing `[B, L]` logits.

## 2.2 Parameters, and why each one is what it is

| Parameter | Value | Justification |
|---|---|---|
| Encoder | `microsoft/codebert-base` | Pretrained on code; GraphCodeBERT shares the tokenizer so swapping is config-only (ablation A5) |
| Window length | 512 tokens | Both encoders cap here; larger is silently truncated by position embeddings |
| Stride | 128 tokens | Overlap so a line split across windows is seen whole |
| Windowing | **on** | Truncation destroys **38.1%** of flagged lines (§2.5) |
| Line cap `n_lines` | 512 | Costs `val` 17.07% of flagged lines, `train` 0.70% — recorded, never tuned on train |
| Encoder LR | 2e-5 | Standard fine-tuning rate for a pretrained transformer |
| GNN LR | 1e-3 | Trained from scratch; 2e-5 barely moves it |
| Loss | Focal, γ = 2.0, auto positive weight | **0.795%** of lines are vulnerable — plain BCE converges to "clean everywhere" |
| Early stopping | `line/top_5_accuracy`, patience 3 | The *loss* improves happily while localization does not — see §2.7 |
| Batch | 16 windows, AMP + gradient checkpointing | Measured best throughput **and** most headroom on a 4 GiB card |
| Seeds | 3 minimum | Fewer has already cost this project two retracted findings |

## 2.3 Implementation practices

- **Registries, not `if/elif`.** Six extension points. A new fusion strategy or graph builder
  is a registration, never an edit to a dispatch block.
- **Config over code (Hydra).** No experiment edits a `.py` file. Every ablation is
  config-only — which is the project's own rule, and a design smell if it is ever violated.
- **Layer enforcement.** `import-linter` fails the build if L0 imports L1. This is why the
  data loader emits `LabelledFunction` (L0) rather than `CodeUnit` (L1).
- **No silent failures.** No bare `except`, no `except: pass`. Every error carries structured
  context.
- **Stubs raise.** An unbuilt component raises `NotImplementedError` rather than returning a
  plausible zero tensor.

## 2.4 What is held fixed so the headline experiment has an answer (ADR-008)

The fusion comparison is the one question here that can be answered **wrongly with nothing
failing** — both arms train, both converge, both produce a number, and the higher one looks
like the answer. So the controls are structural:

- **The branch projections live in the shared base class, not in cross-attention.** Otherwise
  `concat` would be "no projection" against "attention *plus* a projection", and the extra
  parameters would sit inside the arm we hope wins.
- **A line a branch never saw is exactly zero, never a bias vector.** `Linear(0)` is the bias
  — a learnable "this branch is silent here" feature, correlated with function size and
  therefore with the label.
- **The two branch datasets are joined on `unit_id`, never positionally**, and the population
  difference is logged as a run parameter.
- **The line axis is trimmed per batch, and a test asserts that changes no number.**

## 2.5 Correctness findings we can demonstrate

These are the strongest technical-accuracy evidence in the project, because each one is a
silent failure that was caught by measurement rather than by an exception.

| Finding | Measurement |
|---|---|
| **Truncation is not acceptable** | Cutting at 512 tokens destroys **38.1%** of all flagged lines, **44.5%** on the evaluation set. Windowing keeps **100%**. |
| **The corpus's own language column is the worst grammar selector available** | 37.01% clean parses as declared vs **89.14%** best-of-two. 100,735 functions parse cleanly *only* as C++. |
| **The unparseable residue is worse than it looks** | The 20,480 functions no grammar parses cleanly are 10.86% of functions but hold **31.58% of the flagged lines** — they average 68 lines against 26.5. |
| **A project-wise split does not stop function-level leakage** | 207 hashes / 426 functions are byte-identical across partitions **with zero shared projects** (forks and vendored copies). Withheld. |
| **Exceeding VRAM on Windows does not raise** | It pages to host RAM and runs **10–25× slower**. 3 of 24 probe configs exceeded the card and completed with valid numbers. "Did not OOM" is not "fits". |
| **`node.start_point` segfaults the interpreter** | On real corpus input, with no traceback. Lines are derived from `start_byte` instead. |

## 2.6 The formatting leak — the single best slide in the deck

**What happened.** The project's first training run reported line precision **0.985** and
validation F1 that was *flat from epoch 0*.

**Why.** Big-Vul's LineVul release builds `processed_func` by stripping leading whitespace
from every line **except the flagged ones**, which are pasted back verbatim. So:

> **"Does this line start with a space?" predicts the vulnerability label at precision
> 1.0000, with ZERO false positives, on all six partitions.**

The model had learned indentation, not vulnerability.

**The fix (ADR-006).** Strip both ends of every line, applied at L0 *and* L1, both default-on
and idempotent, with an adversarial audit script that re-checks it after any corpus change.

**Why it is worth a slide:**
1. It is a *publishable finding* about a widely-used dataset.
2. It demonstrates the practice that caught it — checking the **learning curve**, not just the
   final metric. A model with nothing left to learn is finished after one epoch.
3. It cost us a run and we kept the run, marked VOID, rather than deleting it.
4. It plausibly affects published baselines — **and we say "plausibly", because verifying it
   requires running their released code, which we have not done.**

## 2.7 Two more bugs found by measurement

- **Evaluation was building an autograd graph for a backward that never came.** `evaluate()`
  had no `no_grad`, and — worse — `transformers` gates gradient checkpointing on
  `self.training`, so checkpointing silently does *nothing* during eval. That made evaluation
  the most expensive pass in the loop. Measured on the largest `val` unit: **10,602 MiB with
  gradients enabled against 1,578 MiB without.** Fixed, with three tests. **No logged metric
  changes**, because nothing in that path reads a gradient.
- **A memory probe is not a result.** Two CPU trials at a reduced training limit were grouped
  with full-corpus runs and shifted a mean before anyone noticed. Both report scripts now
  refuse a run carrying a probe marker or a non-zero limit, structurally.

# CRITERION 3 — RESULTS OBTAINED SO FAR (5 marks)

> *Presents interim metrics, tables, graphs or outputs and provides technically sound

## 3.1 Every metric, explained

**The task:** given a vulnerable function, rank its lines by how likely each is to carry the
flaw. Two families of metric, because there are two ways to use the output.

### Ranking metrics — "did we point at the right line?"

| Metric | Definition | Why it matters |
|---|---|---|
| **Top-1 accuracy** | Fraction of functions where the model's **single highest-ranked line** is a truly flagged line | The strictest possible test. A developer who trusts one suggestion. |
| **Top-5 accuracy** | Fraction of functions where **at least one** truly flagged line appears in the top 5 | Matches how a reviewer actually works — scan a short list. **This is our headline metric.** |
| **IFA** (Initial False Alarm) | Going down the ranked list, **how many wrong lines are inspected before the first right one**. Lower is better. | Directly models wasted developer effort. The metric a practitioner cares about most. |

**Why Top-5 and not Top-10 (which prior work reports):** functions average **31 lines**. At
Top-10 you are already naming a third of a typical function, and the metric starts measuring
function length rather than localization. Top-5 is the harder, more honest cut-off — and it
is also why we cannot be placed directly against LineVul (§3.6).

### Classification metrics — "which lines would we flag?"

| Metric | Definition |
|---|---|
| **Line precision** | Of the lines we flagged, what fraction were truly flagged |
| **Line recall** | Of the truly flagged lines, what fraction we caught |
| **Line F1** | Harmonic mean of the two — the single number for threshold-based use |

**Function-level F1 is degenerate here and must never be quoted.** We score only
line-labelled functions, which leaves no false positives and no true negatives, so it reads
**1.000** by construction. Saying so before a panel asks is worth a mark on its own.

### Statistical practice

Every number is **mean ± 1 standard deviation over 3 seeds**. The project rule is that no
comparison is written down until every arm has ≥ 3 seeds — a rule adopted *after* two
findings had to be retracted (§3.4).

## 3.2 The headline results

**Held-out `val`, 3 seeds each. Validation-selected (see §3.3).**

| Metric | Semantic (LLM-only) | Structural (GNN-only) |
|---|---|---|
| Top-5 accuracy | **0.6141 ± 0.0055** | **0.4302 ± 0.0372** |
| Top-1 accuracy | 0.3513 ± 0.0138 | 0.1750 ± 0.0301 |
| Line F1 | 0.3692 ± 0.0204 | 0.1077 ± 0.0083 |
| Line precision | 0.4732 ± 0.0395 | 0.3206 ± 0.0478 |
| Line recall | 0.3066 ± 0.0418 | 0.0648 ± 0.0045 |
| IFA *(lower is better)* | 11.9315 ± 0.5965 | 20.7752 ± 1.0850 |

- **Semantic runs:** `fc902107…`, `5b177450…`, `e82ff268…` (seeds 42, 1, 2)
- **Structural runs:** `77370d56…`, `0d324da8…`, `3c570cc1…` (`gcn`, depth 4, subtokens on)

**Interpretation.** Top-1 of 0.3513 is roughly **5.6× the base rate** of guessing — the model
has learned something real. The structural branch sits far below the semantic one, and that
is the expected result, not a failure: it is the comparison partner the fusion experiment
needs. A GNN-only number matching CodeBERT would be the *surprising* outcome.

**Notice what the seeds tell you.** Top-5 varies by **under a point** across three seeds while
precision and recall swing by ±0.04 in *opposite* directions. That is the decision threshold
moving, not the model changing — and it is the reason the ranking metric is the headline and
the classification metrics are supporting.

## 3.3 The caveat that must be on the slide

**These numbers are validation-selected, not held out.** Early stopping watched
`line/top_5_accuracy` on `val`, and the reported value is read from the epoch it chose — the
same split, and for Top-5 the same metric. **Top-5 is therefore selected on itself** and is
optimistically biased by an amount this table cannot measure.

`test` (18,442 functions) and `clean_eval` (1,589) **have never been touched**. They are spent
once, at the end of an experiment family, and the fusion family is not finished.

Say it before the panel finds it. "The best this model reached on validation" is the honest
phrasing; "what it would score on unseen data" is not a claim we can make yet.

## 3.4 Two findings we retracted

**This is a strength, not an admission.** Present it that way.

**The depth sweep.** At one seed, depth 6 sat 0.047 Top-5 below depth 4 and was written up as
evidence of over-smoothing. At three seeds per arm, **every pairwise gap between depths 2, 4
and 6 is under 0.6 standard deviations.** There is no resolvable effect. Two separate traps in
one sweep: reading ~2 sd of seed noise as a finding, and reading a depth difference as
*architectural* when the representation itself differs by depth — depth 2 carries a 27.91%
hard recall ceiling against 7.35% at depth 4, so depth 2 losing is expected **before**
over-smoothing is considered at all.

**The subtoken gain's shape.** We predicted the gain would be large at depth 2 and small at
depth 4, because shallow graphs cannot disambiguate identifiers. Measured at three seeds it
is **+0.0567 at depth 2 and +0.0657 at depth 4 — flat**, and 0.27 sd apart. The prediction was
wrong, and disambiguation is not the main thing subtokens do.

**What stands:** identifier subtokens are worth **≈ +0.06 Top-5 regardless of depth** — lifting
the structural branch from 0.3645 to **0.4302**. It is the single largest improvement measured
to that branch.

## 3.5 The three ceilings — what no model here can exceed

| Ceiling | Value | Meaning |
|---|---|---|
| **Line-label noise** | **≈ 30%** | By human audit of 20 sampled functions: 6 of 20 line labels wrong (95% CI [14.5%, 51.9%]). No line-level metric can exceed what this permits. **A held-out score above it is a bug report, not a result.** |
| **Flagged lines with no AST node** | **7.84%** | The structural branch cannot score these at all. 84.8% of them sit in functions no grammar parses cleanly, so a better grammar does not fix it. |
| **512-line cap** | val **17.07%**, train **0.70%** | Flagged lines past the line axis. **24× worse on the reported split than on train** — so the cap must never be tuned on train. |

**These are three different quantities and are never added together or put on one axis.** The
line-noise figure (~30%) is also a *different quantity* from the 19.2% function-level noise
rate and is structurally larger — never present the two as one number.

## 3.6 Comparison with existing work

Quoted from the cited sources on 2026-09-14, kept in `docs/prior_work.yaml`. **Reproduced, not

### Who did what

| System | Approach | Relation to us |
|---|---|---|
| **LineVul** (Fu & Tantithamthavorn, MSR 2022) | CodeBERT fine-tuned for **function**-level classification; lines ranked by the encoder's own self-attention — **no line-level supervision** | Closest to our *semantic* branch, but unsupervised at line level where ours is supervised |
| **LineVD** (Hin et al., MSR 2022) | Statement-level GNN over a code property graph with transformer-encoded statements | **The closest published relative of our structural branch** |

### The numbers

| | Line / statement F1 | Line accuracy | IFA |
|---|---|---|---|
| LineVul **(reported)** | — | 0.65 @ Top-**10** | 4.56 mean / 1 median |
| **LineVD (reported)** | **0.360** | — | — |
| IVDetect **(reported)** | 0.176 | — | — |
| **Our semantic branch** | **0.3692** | 0.6141 @ Top-**5** | 11.93 |
| Our structural branch | 0.1077 | 0.4302 @ Top-**5** | 20.78 |

### What can honestly be claimed

1. **Our semantic branch lands in the same region as LineVD's complete system** — 0.3692
   against 0.360. Same region, different benchmark. The claim is *"not obviously off the
   map"*, and nothing stronger. It is the sentence that says the pipeline works.
2. **Our structural branch is well below LineVD, and that is expected.** 0.1077 against 0.360,
   below even IVDetect's 0.176. But LineVD's GNN reads a full code property graph with
   transformer-encoded statements; ours reads an AST with node types plus identifier
   subtokens. It is a deliberately simple structural baseline against a finished system —
   and it is the argument for why fusion is worth doing.
3. **We cannot be placed against LineVul at all.** They report Top-10, we report Top-5. Top-5
   is the harder cut-off, so 0.6141@5 beside 0.65@10 is **not a loss — but it is not a win
   either.** It is unmeasured. Computing Top-10 from our stored predictions would settle it
   and is cheap; it is not done, so it is not claimed.
4. **Our IFA is clearly worse** — 11.93 against 4.56. Part of that gap is the statistic (our
   mean against their median on a heavily right-skewed distribution) and part is real. Which
   part is unmeasured. **Say this before the panel does.**
5. **Function-level cannot be compared at all**, because ours is degenerate (§3.1).

### Why none of it is like-for-like

- **Different split.** Every published entry uses a **random** function-level split; ours is
  **project-wise**, which is strictly harder. Big-Vul is 65.8% Chrome + Linux, so a random
  split puts near-duplicate functions from the same project on both sides.
- **Different denominator.** We score only line-labelled units; LineVD undersampled its
  training set to class balance. Same metric name, different quantity.
- **Different granularity.** Statements are not lines — a multi-line statement is one unit
  for LineVD and several for us.
- **Possibly different inputs.** The ADR-006 formatting leak may or may not reach their model
  inputs. **UNTESTED** — see below.

### The single most useful number in this section

> A later paper (LEAP, arXiv 2209.10414) re-measures **LineVul** on Big-Vul at **Top-10
> 0.740**, against the **0.65** reported in LineVul's own paper. **Same system, same corpus,
> nine points apart, with no change of method.**

That spread is **wider than most of the improvements published in this literature.** It is the
concrete reason these numbers belong in a table with a caveat column and never as bars beside
ours — a shared axis asserts "these are the same kind of thing" and has no room to take it
back.

### One hypothesis, labelled as such

**Claim:** line-level results trained on the LineVul release of Big-Vul without whitespace
normalization are contaminated by the indentation artefact of §2.6.
**Status: UNTESTED.**
**What would settle it:** running each published system's released preprocessing over the
release and checking whether the leading-space feature survives into its model input.
**Until then** it is never an explanation for a gap between their numbers and ours, and never
a reason ours are lower. It is a claim about other people's work.

# CRITERION 4 — PRESENTATION AND CLARITY (5 marks)

> *Explains the work logically, justifies decisions, and responds accurately to panel
> questions.*

## 4.1 The narrative arc for the deck

1. **The problem.** Function-level detection tells a developer *this file has a bug*. That is
   not actionable in a 300-line function. Line-level localization is.
2. **The idea.** Semantics and structure see different things. Project both onto the same
   line axis and let them attend to each other.
3. **The obstacle we found.** The standard benchmark leaks its own answer through
   indentation. We measured it, fixed it, and our numbers dropped — *correctly*.
4. **Where we are.** Both branches measured over three seeds. The fusion is built and unrun.
5. **What is next.** One experiment: cross-attention against concatenation, under identical
   conditions.
6. **What we will claim.** Not "we beat LineVul". A cleaned benchmark with measured ceilings,
   two honest baselines, and what fusion buys on top.

## 4.2 Decisions, and the measurement that justified each

Every one of these is an ADR with alternatives considered.

| Decision | Alternatives rejected | The measurement that settled it |
|---|---|---|
| Big-Vul via the LineVul release | Devign, ReVeal, PrimeVul as primary | **Only distribution carrying `flaw_line` / `flaw_line_index`** — line labels exist nowhere else |
| Parse with best-of-two grammars | Trust the `lang` column; always C; always C++ | 37.01% / 35.74% / 88.24% vs **89.14%** clean parses |
| Strip whitespace at L0 **and** L1 | Re-indent with a formatter; drop line labels | The formatter changes line counts and destroys the labels; the leak predicts at **precision 1.0000** |
| Withhold cross-split duplicates | Reassign them; keep and report | 207 hashes / 426 functions leak **with zero shared projects** |
| Windowing, not truncation | Truncate at 512 tokens | Truncation loses **38.1%** of flagged lines |
| Two learning rates in the fused model | One shared rate | 2e-5 barely moves a from-scratch GNN; 1e-3 destroys CodeBERT |
| Don't run fusion yet | Run it and see | The phase gate is a human decision, and the numbers it would produce are not yet trustworthy |

## 4.3 Anticipated panel questions, with answers

**"Your numbers are lower than published work. Why?"**
Three reasons, in order of size. We use a **project-wise split**, which is strictly harder than
the random split every published entry uses. We report **Top-5**, not Top-10. And we removed a
formatting leak from the corpus that inflates any number measured with it in place. Whether
their numbers include that leak is untested and we don't claim it.

**"Is 0.6141 good?"**
It is above the measured ceiling's floor and roughly 5.6× the base rate at Top-1, so the model
has learned something real. But **~30% of the line labels are wrong**, so no line-level metric
on this corpus can approach 1.0, and a score that did would be a bug report. It is also
**validation-selected**, so it is the best this model reached on validation, not a held-out
result.

**"Why haven't you run the fusion experiment — that's the whole project?"**
*Updated 2026-09-15.* It is running now. The Phase 3 and 4 gates were signed on
2026-09-15, and the same day we accepted ADR-009: the semantic encoder is frozen and its line
features are computed once and cached, which takes the core two-arm comparison from 20–30
GPU-hours to roughly 90 minutes on the 4 GiB laptop. We checked on the GPU that the cached
features give the same logits as the live encoder, to within the GPU's own run-to-run noise.
The cost is a narrower claim, stated as such: *with a fixed semantic representation*,
cross-attention against concatenation. If the margin is close relative to the seed spread,
the winner and concat are re-run fine-tuned. No fused number is quoted until all three seeds
per arm are in.

**"Why only three seeds?"**
Three is the minimum before any comparison is written down. We adopted that rule *after* one
seed produced two findings that had to be retracted. Five seeds are planned for the headline
fusion comparison specifically.

**"Your GNN branch is much worse than your LLM branch. Isn't that a failure?"**
No — it is the comparison partner the fusion experiment needs. It is also expected: 7.84% of
flagged lines carry no AST node at all, so the structural branch is *structurally* unable to
score them. That ceiling is measured and does not apply to the semantic branch.

**"Function-level F1 of 1.000 — really?"**
It is degenerate and we never quote it. We score only line-labelled functions, so there are no
negatives to get wrong. We flagged it ourselves rather than letting it look like a result.

**"How do we know your results are reproducible?"**
Every run carries a git SHA, a config hash, a seed and a dataset version, and every claim
resolves to a run ID in the experiment ledger. Re-running the split script **verifies**
byte-identity rather than regenerating. The fingerprint is `0ade7483…`.

**"What is genuinely novel here?"**
Two things. **Bidirectional cross-attention over a shared line axis** — prior work uses either
a transformer or a graph, not both fused at line granularity. And **a cleaned line-level
benchmark with its ceilings measured**, which we would argue is the more durable
contribution: nobody can interpret a line-level score on this corpus without knowing that
~30% of its labels are wrong.

**"What are the limitations?"**
Stated, not discovered: ~30% label noise caps everything; the data-flow graph is name-based,
so no aliasing and no scoping — we do **not** claim the model "follows data flow"; 7.84% of
flagged lines have no graph node; the line cap costs the evaluation split 17%; the clean
evaluation set is **not** project-disjoint from train, so it measures label quality and not
generalization; and the fusion result does not exist yet.

## 4.4 Three things to say that will land

1. **"We deleted our own first result."** Run `1843412a…` is kept in the ledger, marked VOID,
   because it learned indentation. Showing the retraction is stronger than hiding it.
2. **"Two of our findings did not survive three seeds, and we withdrew both."**
3. **"Our demo shows no vulnerability scores, on purpose"** — because no valid trained model
   exists to produce one, and a number on a screen is a claim.
